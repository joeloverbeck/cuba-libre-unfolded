## Solid map coordinates and reproduction

Blender5.2.3LTS mechanically extrudes the thirteen VectorCraft source paths (objects38–48,50,52). The current source is `atlas-map.vectorcraft`, refined after the owner requested more usable province area and then closer resemblance to the actual board. It contains only the map profiles and geography labels; `atlas-map-profiles.svg` exports only its thirteen outlines. City/EC cubic curves are sampled at24 equal steps per segment (96 perimeter vertices per ellipse). The conversion is Blender `(X,Y,Z)=((x−700)/100,(600−y)/100,height)`, and the exported glTF/Bevy coordinates are **`(X,Y,Z)=((x−700)/100,height,(y−600)/100)`**. All mesh origins remain zero; vertices already carry board placement. Use scene0 without a further axis rotation or per-region recentering. Root scaling/translation is permitted for whole-board placement and must apply equally to labels and pieces. Do not apply the temporary native depth expansion: use the current authored profiles directly.

Province tops are at0.14 units, cities at0.24, ECs at0.28; bottoms at0. The one-segment bevel width is half the selected stroke width in map units (province0.015, city/EC0.01); its material comes from that same authored stroke. Top and side colors come from the selected fill, with sRGB converted to linear PBR values. No displacement, relief terrain, borrowed board textures or automatic rearrangement was introduced. Label planes use their recorded bounds divided by100, centered over the corresponding source rectangle at that region's top+0.002; image alpha keeps their unprinted area transparent. Use the Bevy coordinate conversion above when placing them. Runtime Support/Control/markers and grouped pieces must not be baked into those planes.

Node names and `space_id` extras are `pinar-del-rio`, `la-habana`, `matanzas`, `las-villas`, `camaguey-province`, `oriente`, `sierra-maestra`, `havana`, `camaguey-city`, `santiago`, `ec-pinar-la-habana`, `ec-las-villas-camaguey`, `ec-oriente-sierra`. Names join exactly to `labels.json`; map them explicitly to the rules model's own IDs. Renderable material primitives can be separate children of a named glTF node. Attach picking/space identity at that node and resolve child hits to its owner; do not mistake border and fill for two spaces. City/EC geometry overlaps its source-contact provinces in plan and sits higher, so nearest-surface picking must select the raised space.

To reopen, open `art/atlas/atlas-map.blend` in Blender and select scene **Cuba_Atlas_Regions**. Collection **Atlas_Regions** owns runtime mesh sources; **Authoring_preview_only** owns the preview camera/light. The original default Scene/Cube/Camera/Light were preserved. ## Interface palette

The `Atlas` colour variables of the selected FigCraft layouts own the interface palette ([foundation 4](../../docs/foundation/04-art-and-assets.md), "Layout authority"). `palette-sources.sha256` lists the selected layouts' `.figcraft` files. Each layout keeps its own copy of the collection, so each has an export:

- **Exports:** `atlas-<layout>.variables.json` is FigCraft's `variable.export` of the layout's `Atlas` collection, in the local variables JSON format that `variable.import` reads. No one edits it by hand. FigCraft CLI 0.18.1 (`storytold/figcraft@44d61a5a`) wrote #53's exports; a later layout's specification names the FigCraft build that wrote its own.
- **Source hashes:** `palette-sources.sha256` records each `.figcraft` file's SHA-256 at the time of its export. It is a test record, not a launch manifest.
- **Check:** the `palette` module of the tabletop declares each runtime colour together with the variable it stands for. Its unit tests fail when a colour differs from that variable in any layout that defines it, when no layout defines the variable, or when a `.figcraft` file no longer has its recorded hash. `scripts/check` refuses a colour literal anywhere else in `src/` unless its line says `// own colour: <reason>`.

Older VectorCraft-authored components keep their own colours until a layout decision reopens them (foundation 4), so they are not declared there. The victory tag's text colours are an example (`victory.rs`). Piece colours are a separate palette, listed under "Counted solid pieces and shared camera"; two of them equal faction variables, but they do not stand for them.

Some declared variables carry colours that VectorCraft art also paints: `map` is the sea the map camera clears the window to ([MAIN-VIEW.md](MAIN-VIEW.md)), which the authored [water frames](water/README.md) also paint, and `faction/government` and `faction/syndicate` are also the Government and Syndicate colours of the retired `atlas-ui` and `atlas-reader` (their 26July and Directorio colours differ from the variables). Changing one of these in FigCraft therefore also reopens those VectorCraft sources.

**Refreshing after a layout changes.** For each changed `.figcraft`, open it with FigCraft's `file.open` ([art-tools.md, "FigCraft pitfalls"](../../docs/agents/art-tools.md#figcraft-pitfalls)). Then run `variable.export` with `{"collections": ["Atlas"], "format": "json", "path": "<main checkout>/art/atlas/atlas-<layout>.variables.json"}` and move the file into your worktree ([art-tools.md, "File boundaries"](../../docs/agents/art-tools.md#file-boundaries)). Rewrite the hashes from the checkout root:

```sh
sources=$(awk '{print $2}' art/atlas/palette-sources.sha256)
sha256sum $sources > art/atlas/palette-sources.sha256
```

The hashes only prove which source an export was taken from, so always re-export before rewriting them. A newly selected layout gets a line in `palette-sources.sha256` and an entry in the `palette` tests' export list; the tests check that the two agree. A colour the runtime newly takes from a variable joins the module's declarations.

## Launch admission

Before it creates or replaces a save, the app checks every manifest that `src/assets.rs` lists in `MANIFESTS`, decodes the PNGs, registers the fonts and admits the real scene and render path. A missing or altered asset refuses at launch.

`runtime.sha256` and one manifest per selected design are each named in `MANIFESTS`. Art is in no save's identity ([ADR 0003](../../docs/adr/0003-a-save-opens-by-exact-replay.md), [docs/agents/saves.md](../../docs/agents/saves.md)): adding or changing a manifest does not change what a save records or which saves open, and does not weaken source, checksum or replay admission.
